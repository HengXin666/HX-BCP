# Agent Note: 8325 serves the new console, human lane via a console session cookie

Status: implemented

## Problem

8325 served the old local-browser bundle from `packages/browser/src/hx_browser/web/`. The new console (`apps/console-web`) only ran under vite dev on 8940, whose Node side injected `x-bcp-human-token`. Served statically by 8325 there is no Node side, and the token must never be in a static file.

## Decision

- `apps/console-web/vite.config.ts`: `build.outDir` = `packages/browser/src/hx_browser/web`, `emptyOutDir: true`. Every build wipes the directory first, so no old file survives.
- Frontend calls `/api/v1/*` directly (same path as 8325). vite dev proxies `/api/v1` to 8325 unchanged; cache stats go through a new read-only `GET /api/v1/cache/stats` on 8325 (`api_cache.py`), because 8898 sends no CORS headers.
- Human proof for the static console: a session cookie.
  - `POST /api/v1/lane/session {token}` (`api_lane.py`): same-origin page only, token checked by `lane.human_token_valid`, then `Set-Cookie: bcp_human=<unix>.<hmac_sha256(token, label+unix)>; HttpOnly; SameSite=Strict; Path=/api/v1; Max-Age=43200`.
  - `lane.decide(..., session, from_self)`: human admitted when the token header is valid, or the session is valid and `from_self`.
  - `lane.same_origin(host, origin, fetch_site)`: Sec-Fetch-Site decides when present (must be `same-origin`), else Origin must equal `http(s)://<Host>`, no signal means false.
  - `lane_guard.decide_from(conn)` reads header, cookie and those signals, for HTTP and websocket alike.
- Console: `HumanGate` asks for the token once (`cat ~/.bcp/human.token`), keeps nothing, renders the tabs only after the server says human.
- `packages/browser/frontend` is deprecated: its `vite.config.js` throws on load, README says so.

## Why these and not

- **Write the token into index.html or a JS file at serve time**: rejected by the owner, and any local process can GET `/` and read it, so curl would get human identity for free.
- **Trust Origin or Sec-Fetch-Site alone**: curl can set both. They only gate a cookie that curl does not have.
- **SameSite alone**: other localhost ports are same-site, so a page on localhost:9999 would ride the cookie. Same-origin check closes that.
- **Cookie holding the token**: an hmac keyed by the token is enough to verify, leaks nothing, and dies when `bcp-lane issue` rotates the token.

## Consequences

- One paste per 12 hours per browser. Rotating the token logs every console out.
- With `settings.api_key` set, the existing api key middleware 401s static assets too, the console can not load (unchanged, pre-existing).
- Browsers without Sec-Fetch-Site send no Origin on same-origin GET, so they are refused (modern Chromium and Firefox send it).
